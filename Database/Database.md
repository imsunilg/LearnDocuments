# Database design - LearnInsuranceDB

- Engine: PostgreSQL 16, database `LearnInsuranceDB`, schema `learninsurancedb`
- Scripts: `LearnDB/` (applied in order by `LearnDB/setup.ps1`): `schema/` -> `tables/` -> `functions/` -> `indexes/` -> `seed/`
- Rule: **no SQL in application code** - the API only calls `fn_<entity>_<action>` functions, which return JSON (jsonb) already in camelCase.

## Decision (Day 07): BIGINT identity vs UUID
| | BIGINT identity | UUID |
|---|---|---|
| Size / index speed | 8 bytes, sequential, fast | 16 bytes, random inserts fragment indexes |
| Readability | Easy in URLs, logs, support calls | Opaque |
| Guessability | Enumerable (mitigated by authorization) | Hard to guess |
| Distributed generation | Needs the DB | Client-side generation possible |

**Chosen: `BIGINT GENERATED ALWAYS AS IDENTITY`** for all primary keys, plus a human-readable business code
(`CUST00001`, `POL-2026-000001`) where users need one. A single database, join-heavy reporting and readable
support tickets outweigh UUID benefits. Authorization checks (not obscurity) protect records.

## Audit fields (every table)
`id, created_date, created_by, modified_date, modified_by, is_active` - `is_active = false` is the soft delete.

## Conventions
- Tables/columns `snake_case`; PostgreSQL functions return `jsonb` produced through `fn_to_camel(to_jsonb(row))`, so the API/React see camelCase.
- Lists return `{ items, totalCount, page, pageSize }`.
- Business errors are raised with `RAISE EXCEPTION ... USING ERRCODE = 'P0001'` (400) / `'P0002'` (404); constraint violations map to 409/400 in the API.
- Generic CRUD functions and views are generated by `LearnDB/tools/gen-crud.mjs` from `LearnDB/tools/entities.mjs`.
